# 中文OCR QA：服务器部署、下载与运行命令手册

## 1. 现状与目录

本轮SSH连接被拒，因此以下是**已实现、合成测试通过的服务器操作入口**，不是服务器已下载或真实27B已跑通的声明。代码在公开独立仓库`Tiachi/chinese-ocr-qa`，不上传数据或模型。

|用途|默认路径|
|---|---|
|代码（拟部署）|`/mnt/sfs/ltj/project/chinese-ocr-qa`|
|独立CPU/HTTP环境|`/mnt/sfs/ltj/runtime/ocr-qa`|
|服务器用户配置|`/mnt/sfs/ltj/ocr_qa/config/unirec9.json`|
|原始九子库|`/mnt/sfs/unimoe_dataset/omni/UniRec40M`|
|中间产物/检查点|`/mnt/sfs/ltj/ocr_qa/unirec9-v1`|
|导出的原始图像字节|`/mnt/sfs/unimoe_dataset/training/images/UniRec_Chinese_OCR_QA`|
|正式JSONL注册路径|`/mnt/sfs/unimoe_dataset/omni/json/UniRec_Chinese_OCR_QA.jsonl`|
|正式README注册路径|`/mnt/sfs/unimoe_dataset/omni/readmes/UniRec_Chinese_OCR_QA.md`|

用户配置在代码目录外，更新不会覆盖它。`config/pipeline.json`可配置所有入口、工作/交付路径、清洗阈值、API模式/并发及配比；`config/service.json`单独配置模型Python、vLLM目录、权重、TP/DP与端口。正式操作要求干净checkout，不自动stash/reset/clean。

下载原始数据约253.7GB。HWDB原库有分片，派生合并LMDB另外约192GB；后续原图字节导出还会占空间，不能只预留253.7GB。下载器检查原始文件+一个最大文件的合并余量；**不是全流程总空间保障**。标注/SQLite/模型缓存应另留空间。保留原分片，禁止为省空间擅自删除原始文件。

## 2. 部署

在服务器独立chinese-ocr-qa checkout中：

```bash
cd /mnt/sfs/ltj/project/chinese-ocr-qa
bash scripts/sync.sh
bash scripts/run.sh deploy
```

部署使用Python3.10+建立独立venv，安装Pillow/ijson/lmdb/DataTrove，再跑合成自测；不安装torch/vLLM、不改NPU运行环境、不请求模型、不下载生产数据。pip直连清华源，子进程禁用个人代理及额外pip索引；不修改全局配置。若现有python3太旧，设置`OCR_QA_BOOTSTRAP_PYTHON`为已有3.10+解释器路径再运行同一部署命令。

## 3. 先核查源，再并发下载

```bash
bash scripts/run.sh probe
bash scripts/run.sh download-bench
```

`probe`只查询作者ModelScope目录。当前结果是仅2说明文件，没有数据；HF下载不会假装来自ModelScope。`download-bench`在服务器对配置源各取4MiB，验证206响应并报告时间/吞吐。默认比较官方HF与hf-mirror；**本轮没有测出哪个在服务器快，也没有已验证“比hf-mirror更快”的第三方站点。** 官方源可能重定向到官方存储/CDN，不等于另有可承诺速率的镜像。

按配置源中本机实测较快者下载全部九库：

```bash
bash scripts/run.sh download-fast
```

默认最多4文件×8分段=32个HTTP请求，每段64MiB；只下载固定revision中的57个文件，不扫描其他子库。每文件合并后验证上游LFS SHA256或普通文件Git对象SHA1；Range不被支持时停止，不偷偷变成32次整文件下载。完成范围缓存可续传，已存在原始文件先核验，不覆盖不同内容。

若要指定另一个**你认可的HF兼容HTTPS镜像**：

```bash
bash scripts/run.sh configure --mirror https://你的镜像域名
bash scripts/run.sh download
```

也可编辑服务器JSON的`download.benchmark_urls`，加入该镜像后用`download-fast`测速选源。只有`https://域名`，不填签名URL、账号或个人代理。配置`files_concurrency`、`segments_per_file`可调并发，总HTTP上限128；先观察共享存储与网络，不把并发翻倍等同于吞吐翻倍。当前代码是无认证公共源下载，不绕过门禁。

**想先最快验证整条链路：** 只下载TAL约1.36GB，后续pilot也只指定它：

```bash
bash scripts/run.sh download-fast --subset TAL_OCR_HW
bash scripts/run.sh inspect --subset TAL_OCR_HW
```

全九库下载后合并HWDB分片、查看所有字段：

```bash
bash scripts/run.sh assemble
bash scripts/run.sh inspect
```

`assemble`按清单顺序合并，只写work_root派生LMDB，不修改原分片；已有合并文件必须有对应收据，未确认的同名文件不会覆盖。中断留下临时合并文件会保留供人工处置；不自动删除大文件。`inspect`每个标注最多3条，只打印结构，不解码图片、不调用模型。

## 4. 配置/复用本地Qwen3.8-27B

已有可用OpenAI兼容接口时，只需：

```bash
bash scripts/run.sh configure --base-url http://IP:PORT/v1 --model qwen3.8-27b --mode vision --concurrency 64
bash scripts/run.sh api-check
```

`--model`必须等于`/v1/models`实际返回的served name，大小写一致。接口要求key时用环境变量`OCR_QA_API_KEY`，不写进配置、Git或命令参数。`api-check`只GET模型列表，不证明视觉可用；后续pilot会验证真实图片请求。

**没有可复用服务且16卡空闲时**，另开终端：

```bash
bash scripts/run.sh service
```

参考本项目已经成功使用过的配置：权重`/mnt/sfs/ltj/modelscope/Qwen3.8-27B`，Python`/usr/local/python3.12.13/bin/python3`，vLLM`/vllm-workspace/vllm`；TP2/DP8，前缀缓存、align、chunked prefill、async scheduling、decode graph。图片模式允许1张图，**不传`--language-model-only`**；默认上下文8192、每rank32seq、HTTP并发64，先实测再加到128/256。

脚本在原生解释器下用`torch_npu.npu.mem_get_info`逐卡检查，避开你之前通用accelerator allocator报错；显式设置`VLLM_PATH`，避免之前KeyError。发现端口占用/显存不足就停止，**不会终止现有服务**。这是参考既有记录的视觉启动配方，本轮未在910C上运行验证，图编译/具体版本兼容性仍看真实启动日志。

`service`前台持续运行，另一终端跑pilot。关闭只需该服务终端Ctrl-C，不提供跨服务pkill。若权重路径或环境不同，复制service.json到服务器配置目录编辑，再用`service --service-config /实际路径/service.json`，不需修改代码。

若暂时只有之前的文本服务：

```bash
bash scripts/run.sh configure --base-url http://IP:PORT/v1 --model 实际served-name --mode text
```

这只能快筛文字一致性，最终summary会写`TEXT_PROXY_ONLY_NOT_VISUAL_VERIFIED`，不能替代图文质量清洗。默认推荐vision。

## 5. 小规模、人工核对、全量

TAL小库接口试跑：

```bash
bash scripts/run.sh pilot --subset TAL_OCR_HW --limit 100
```

全九来源试跑（11份label，每份前100条，最多1100条，清洗后可能更少）：

```bash
bash scripts/run.sh pilot --limit 100
```

逐阶段输出目录在work_root下。pilot用于字段/映射/请求/吞吐排错，**前缀不是随机准确率抽样**。看`01_mechanical`的review原因、`03_quality`的accepted/review，再人工查看不同来源图文配对。阈值默认8，未校准；中文标签不是流畅性作文，不应被改成语义更顺的文本。

先机械阶段不请求模型：

```bash
bash scripts/run.sh mechanical
bash scripts/run.sh draft
```

确认规则与试跑后执行完整管道：

```bash
bash scripts/run.sh run
```

已提交阶段按输入身份/配置/代码SHA复用，完整原图不重复写；已成功模型请求按精确prompt/model/payload缓存复用。**未提交的机械阶段会重跑该阶段；不是逐图片进度恢复。** 请求阶段中断后可复用已成功缓存。技术失败进入review，普通重跑不会自动重发；明确重试已知错误用`run --retry-errors`。只有pending没有结果的请求默认阻止重发，先核对缓存与服务情况；不自动假设它没执行。

默认不指定总QA数，按OE/MCQ实际可用容量求最大可行40的倍数；也可在配置中设置`mix.target_qa`。40整除才能同时满足70/30及MCQ四选项精确均分。不足时明确报错，不复制样例硬补。九子库每个至少1条，缺源则停止交付；来源限额按容量水位分配，既不等于原始比例，也不声称已优化训练配方。

## 6. 产物、注册与验收

成功时`DELIVERY_PASS`给出精确的`04_delivery/<run>`路径，里面有：

- `UniRec_Chinese_OCR_QA.jsonl`：human/gpt、images相对路径、modal_mask1，无新增token估算字段，原标注字段顶层保留。
- `attributes.jsonl`：题型、OCR粒度、模型分数、审查模式和图像哈希。
- `README.md`、`stats.md`、`summary.json`：QA/独立图片/来源/题型/MCQ字母/候选容量。
- `receipt.json`：配置、输入阶段绑定、代码SHA、输出大小/SHA。

检查这一产物再注册（替换命令末尾的精确run路径）：

```bash
bash scripts/run.sh register --delivery /mnt/sfs/ltj/ocr_qa/unirec9-v1/04_delivery/实际run目录
```

只建立同文件系统无覆盖硬链接；同名正式路径已属于别版就拒绝，不覆盖。跨文件系统硬链接失败时保留完整delivery，不自动复制数百GB数据。README使用中文四节及字段/路径表。实际发布JSONL、图片、README仍须按当前`data_format.md`验收，本项目不拿自己的schema自证严格合规。

当前holdout默认未配置，只能保证相同像素不重复；如有评测图像SHA清单填`mechanical.holdout_sha256_file`。不声称实现未知原页级分组、近重复检索或完整评测去污染；本版不自动产出随机验证集。
